# /audit — 项目体检与清理

通读整个项目，找出所有**坏掉的、不一致的、低效的、已经不需要的**东西。
**有把握的就修掉，其余的列出来给用户审。**

如果用户在命令后附带了参数（例如一个目录、一个模块名或 "只看性能"），只在该范围内执行；否则覆盖整个项目。

## 0. 安全前提

- 先看版本控制状态（如 `git status`）。如果有未提交的改动，**不要碰那些文件里用户自己的改动**，并在报告开头提醒用户；最好建议用户先提交或开分支。
- 不推送、不发布、不改 CI 密钥、不升级大版本依赖、不改数据库结构或迁移文件。
- 不删除任何可能被外部使用的东西（公共 API、导出符号、CLI 参数、配置键、被动态引用的文件），这类只列出不动手。

## 1. 摸清项目

1. 列出目录结构，识别语言、框架、包管理器、入口文件。
2. 阅读 README、构建/配置文件（package.json、pyproject、Cargo.toml、go.mod、Makefile、CI 配置等），弄清如何构建、测试、lint。
3. **建立基线**：能跑的构建 / 测试 / lint / 类型检查都先跑一遍，记录原本就失败的项。后面每次修改都要能和这个基线对比。

## 2. 通读并分类问题

逐个目录、逐个文件阅读（大项目可以按模块并行处理），按下面四类收集问题，每条都记录 `文件:行号` 和证据：

**坏掉的**
- 编译 / 类型错误、失败的测试、运行时必然出错的代码路径
- 引用了不存在的文件、模块、函数、环境变量、配置键
- 失效的脚本、错误的路径、过期的命令、坏掉的文档链接
- 明显的逻辑错误（错误的条件、遗漏的 await、资源未释放、吞掉的异常）

**不一致的**
- 文档 / 注释 / 类型声明与实际代码行为不符
- 同一件事多种写法：命名风格、错误处理方式、日志方式、配置来源
- 多处重复定义的常量、版本号、依赖版本互相冲突
- 锁文件与清单文件不同步

**低效的**
- 循环内重复的 I/O、查询（N+1）、可提出循环的计算
- 可以复用却被复制粘贴的代码
- 不必要的同步阻塞、重复解析、重复构建
- 过重的依赖只用了很小一部分

**已经不需要的**
- 未被引用的文件、函数、变量、导出、样式、资源
- 未使用的依赖、过时的 polyfill / 兼容代码
- 被注释掉的大段代码、已完成或已失效的 TODO
- 残留的调试输出、临时文件、空文件、废弃配置

## 3. 判断"有把握"

一个问题只有**同时满足**以下条件才直接修：

- 问题是确定的，有明确证据（不是"可能"、"看起来"）
- 修复是局部的、意图明确的，不改变对外行为（除非原行为本身就是 bug）
- 修复后可以验证（构建 / 测试 / lint 通过，或通过搜索确认无引用）
- 不涉及产品决策、架构取舍或用户偏好

否则一律放进"待审清单"，不要动手。拿不准时，归入待审。

## 4. 修复

- 一次只修一类或一处，改完立即重新跑相关检查；比基线更差就回滚这次修改并把它移入待审清单。
- 删除前全局搜索确认没有引用（包括字符串形式的动态引用、配置、脚本、文档）。
- 保持项目已有的代码风格，不做顺手的大范围格式化或重构。
- 全部修完后再完整跑一次基线检查。

## 5. 报告

最后用用户的语言输出一份报告，结构如下：

### 已修复
按四类分组，每条一行：`文件:行号` — 问题 — 怎么修的。

### 待你审核
按优先级（高 / 中 / 低）排序，每条包含：
- `文件:行号`
- 问题是什么、证据是什么
- 建议的修法
- 为什么没有直接修（风险 / 需要决策 / 无法验证）

### 验证结果
基线 vs 现在：构建、测试、lint 各自的结果。如有原本就失败的项，单独说明。

### 未覆盖
没检查到的部分及原因（例如无法运行的测试、过大的生成文件、二进制资源）。

报告结束时询问用户：待审清单里要处理哪几条。
